# Stage 3D.1A — إغلاق نزاهة التكامل النهائي

**التاريخ:** 2026-07-12

**الحالة:** تقوية محلية ضيقة النطاق؛ لا تكامل حي ولا مخزن خلفي دائم.

**نطاق البيانات:** `temporary-demo` داخل مختبر قابل للتخلص منه.

## الفجوات الثلاث

1. كان ممكناً تركيب هوية المصدر من عقدتين مختلفتين، أو قبول جهة موجودة في الرسم من دون إثبات ارتباطها بنشاط الموائم.
2. كان الحدث الناتج يُفحص بنيوياً، لكن لم تكن هوية التسليم كاملة مربوطة حرفياً بالفعل الذي اجتاز التحقق.
3. كان تمييز الإعادة المطابقة عن تعارض مفتاح التكرار يعتمد جزئياً على ذاكرة `ActionGateway`، ولذلك لا يصمد عند إنشاء بوابة جديدة فوق المستودع نفسه.

## التصحيحات

### رسم المصدر

يقبل `ProvenanceResolver` bundle فقط عندما:

- تحمل عقدة source-record واحدة كلاً من `sourceRecordId` و`sourceSystemId` المتوقعين.
- توجد عقدة adapter-normalization واحدة تحمل `adapterId` و`adapterVersion` المتوقعين.
- توجد عقدة operational-event واحدة تحمل `eventId` المتوقع.
- توجد جهة واحدة تمثل نظام المصدر أو الموائم المتوقع.
- تكون هويات العقد والعلاقات فريدة، وتوجد كل نهايات العلاقات.
- يثبت الرسم السلسلة نفسها: source used by activity، event generated by activity، activity associated with expected agent، وevent has the same primary source.
- يكون الرسم متصلاً، غير ملتبس، وفي `stateContext` نفسه.

العقد البديلة المنفصلة، المصدر المركب، الارتباط بجهة خاطئة، وتكرار العقد المطابقة كلها أخطاء مانعة. `productionIdentity` و`authoritativeDeviceTime` يبقيان مجهولين صراحة؛ النص المحلي للمنفذ ووقت الجهاز ليسا هوية إنتاجية أو وقتاً سلطوياً. هذا العقد مستوحى من مفاهيم provenance ولا يدعي مطابقة W3C PROV.

### ربط الفعل بالحدث

بعد إعادة حساب البصمة القانونية لـ`ActionSubmission` وبناء `OperationalEvent`، تقارن البوابة قبل الإلحاق:

- `resultingEventId` مع `eventId`.
- `targetEntityId` و`stateContext`.
- `evidenceRefs` و`provenanceRefs`.
- `payloadHash` و`idempotencyKey` و`offlineSequence`.
- `sourceRecordId` و`sourceSystemId`.
- `adapterId` و`adapterVersion`.

ثم تعيد حل الأدلة والمصدر مقابل الحدث المبني. أي اختلاف يوقف المسار قبل `append`؛ لا يوجد حدث جزئي ولا تثبيت لمفتاح التكرار.

### التكرار والتعارض

المستودع المحلي نفسه يحتفظ ببصمات الاصطدام. بصمة محتوى الحدث تشمل العقد القانوني كله عدا `revision` الممنوح لترتيب السجل، كي تبقى إعادة الفعل المطابق مطابقة حتى لو أُعيد بناؤها بعد وجود الحدث:

| الاصطدام | البصمة مطابقة | البصمة مختلفة |
| --- | --- | --- |
| مفتاح التكرار نفسه | duplicate | conflict |
| هوية الحدث نفسها | duplicate | conflict |
| هوية المصدر نفسها | duplicate إذا تطابقت حمولة المصدر القانونية | conflict إذا اختلفت |

نتيجة conflict تحمل نوع الاصطدام وهوية الحدث القائم والوارد والبصمتين وشرحاً عربياً. تُجهز القوائم والفهارس التالية خارج الحالة ثم تُبدل معاً بعد اجتياز كل الفحوص. لذلك تعمل الدلالة بعد إنشاء `ActionGateway` جديد فوق **نفس repository instance**، لكنها لا تدعي الصمود بعد إعادة تشغيل العملية لأن المستودع ما زال في الذاكرة.

## العقد المحفوظة

- مستودع الأحداث يعرض `append/get/list/count` فقط، ويعيد defensive clones.
- reset يستبدل مستودع المختبر بالكامل ولا يمس baseline.
- سياقات `temporary-demo` و`baseline` و`scenario` لا تختلط.
- بقيت storage schema `8` وquarantine وترتيب lifecycle وحل الأدلة وفصل درجتي الأولوية كما هي.
- بقيت هوية `PROJECTION-v1-<sha256>` وهوية الأمر ومحاولة التسليم والتحقق الكامل من تزامن المخرجات كما هي.
- المختبر lazy-loaded، ولم تُضف SDK أو dependency جديدة.

## ما يبقى محلياً ومحاكياً

المصدر والجهة والأدلة والصحة والوقت والتسليم والمخرجات كلها fixtures محلية. لا يوفر هذا العمل authentication أو authoritative time أو durable identity أو encryption أو concurrency أو backend transaction أو chain of custody أو اعتماد معيار خارجي.

## قبل مختبر تكامل خارجي

يلزم قرار أحمد بحالة استخدام واحدة، عقد بيانات مجمد، نظام مصدر ومالك وسلطة حقيقيون، تعريف هوية ووقت موثوقين، مخزن دائم ذري، سياسة أمن وخصوصية واحتفاظ، خطة قبول موائم، rollback، ومقاييس نجاح وفشل. هذا المستند لا يصرح Stage 3E ولا يبدأ اتصالاً خارجياً.

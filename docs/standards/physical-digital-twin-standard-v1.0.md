# معيار ميادين للتوأم الرقمي الفيزيائي

**معرّف المعيار:** `MEIOS-PDT-STD-001`

**الإصدار:** `1.0.0`

**الحالة:** معتمد كأساس تصميم إلزامي

**تاريخ السريان:** 2026-07-11

**المالك وصاحب الاعتماد النهائي:** أحمد

**النطاق:** جميع مشاريع ومنتجات Mayadeen Event Intelligence OS الحالية والمستقبلية

## 1. قرار الاعتماد

هذا المعيار هو المرجع الإلزامي لكل عمل يتضمن مجسمًا فيزيائيًا، أو طباعة ثلاثية
الأبعاد، أو إسقاطًا ضوئيًا، أو ربطًا بين المنصة الرقمية ومخرج فيزيائي.

الإصدار `1.0.0` مجمّد ولا يجوز تغييره داخل مشروع بعينه. أي تطوير مستقبلي يصدر
كإصدار جديد منضبط، مع الحفاظ على التوافق قدر الإمكان. لا يجوز للمورد أو الفريق
استبدال مادة أو جهاز أو عقد تكامل أو قاعدة هوية من تلقاء نفسه.

يعتمد المعيار **العقود والنتائج المطلوبة** ولا يعتمد علامة تجارية واحدة. أسماء
الطابعات والبروجكترات والبرامج توجد فقط في
`docs/standards/approved-equipment-list.md` حتى يمكن استبدالها بمكافئ مؤهل دون
كسر المنصة أو المشاريع السابقة.

اعتماد هذا المعيار لا يعني بدء Stage 6، ولا يعد تصريح شراء أو تركيب أو ادعاء بأن
المعايرة الفيزيائية مطبقة حاليًا. التنفيذ والشراء والتجارب المادية تبقى خاضعة
لميثاق البحث والتطوير وموافقة أحمد الصريحة.

## 2. الهدف

يضمن المعيار أن كل فعالية تستخدم المحرك نفسه، بينما تتغير بيانات الفعالية
وتصميم موقعها فقط. النتيجة المطلوبة هي منظومة قابلة للتكرار تحقق السلسلة التالية:

```text
Mayadeen Event Intelligence OS
→ عقد مكاني وتشغيلي بإصدار محدد
→ Projection Gateway
→ Vendor Adapter
→ Projection Renderer
→ Video Output
→ Projector
→ Physical Model
```

المنصة هي مصدر الحقيقة التشغيلية. المجسم والبروجكتر واجهتا عرض وتنفيذ، ولا
يملكان منطق الأعمال أو الحالة الأساسية.

## 3. نطاق المعيار

يشمل:

- خط إنتاج الأصل الهندسي إلى نموذج رقمي ومجسم قابل للتصنيع.
- هوية العناصر وربطها بين البيانات والهندسة والقطع الفيزيائية.
- الإحداثيات والمقاييس وتحويلها بين الأنظمة.
- تصنيع المجسمات المعيارية وتجميعها وتشطيبها.
- تصميم الإسقاط، ومخرجات العرض، والمعايرة وحفظ ملفاتها.
- الربط اللحظي بين لوحة التحكم وProjection Gateway.
- حالات الفشل، العمل المحلي، الاستعادة، والسلامة.
- الاختبارات، القبول، التسليم، والإصدارات.
- إدارة التغيير والاستثناءات.

لا يشمل هذا الإصدار:

- اعتماد بروجكتر أو طابعة دون اختبار قبول فعلي.
- الواجهة الميكانيكية المتحركة المستوحاة من MIT inFORM.
- الحساسات والكاميرات والبيانات الحية.
- محاكاة الحشود أو الذكاء التنبؤي.
- تنفيذ Backend أو سجل تدقيق إنتاجي.

## 4. المبادئ الإلزامية

1. المنصة عامة للفعاليات وليست خاصة بعميل أو فعالية واحدة.
2. كل عنصر مكاني أو فيزيائي له ID دائم وفريد.
3. النموذج الهندسي والحالة التشغيلية منفصلان.
4. `temporary-demo` و`baseline` و`scenario` لا تختلط.
5. Projection Gateway لا يحتوي منطق أعمال.
6. كل مورد خارجي يتصل من خلال Adapter موثق وقابل للاستبدال.
7. لا يعتمد التشغيل التشغيلي عند عدم تطابق إصدارات النموذج والمجسم والمعايرة.
8. 2D و3D والمجسم الفيزيائي تمثيلات متكاملة وليست مصادر حقيقة مستقلة.
9. لا تستخدم Digital Keystone أو Warp لتعويض تركيب ميكانيكي خاطئ بصورة أساسية.
10. لا يعلن نجاح أي تركيب قبل اجتياز اختبارات القبول داخل الغرفة الحقيقية.

## 5. ملفات التنفيذ القياسية

يختار كل مشروع ملفًا واحدًا عند البدء، ويجمّده داخل Project Configuration.

| الملف | الاستخدام | الحدود الإرشادية |
| --- | --- | --- |
| `PDT-S` | نموذج داخلي صغير أو اختبار قيمة | مساحة نشطة حتى نحو 600×600 مم، وبروجكتر واحد بعد الدراسة |
| `PDT-M` | الملف المرجعي الافتراضي | قاعدة مرجعية 1200×900 مم، ووحدات تصنيع مفضلة لا تتجاوز 300×300 مم |
| `PDT-L` | مواقع كبيرة أو هندسة مرتفعة ومعقدة | أكبر من `PDT-M` أو متعدد البروجكترات أو يحتاج Rig متخصصًا |

الأبعاد ليست قالبًا يجبر كل موقع على الشكل نفسه. الملف يثبت واجهات التركيب
والاختبارات وحزمة التسليم؛ أما المقياس، والارتفاعات، وعدد الوحدات والبروجكترات
فتحددها دراسة المشروع.

## 6. خط الأصل الواحد

يجب أن ينتج كل مشروع من أصل هندسي معتمد واحد:

```text
Authoritative CAD/BIM/3D Source
├── Runtime GLB/GLTF
├── Fabrication STL/3MF
├── Entity Mapping Manifest
├── Physical Part Register
└── Projection Surface Manifest
```

ممنوع تعديل نسخة الطباعة ونسخة المنصة بصورة مستقلة دون تحديث المصدر والـManifest.

### 6.1 Model Manifest الإلزامي

يحتوي على الأقل:

- `modelId`
- `modelVersion`
- `sourceFileHash`
- `runtimeFileHash`
- `fabricationPackageHash`
- `units`
- `canonicalCoordinateFrame`
- `runtimeCoordinateFrame`
- `transformVersion`
- `entityMappingVersion`
- `physicalRevision`
- `approvedBy`
- `approvedAt`

## 7. الإحداثيات والتحويل

مرجع التبادل المكاني لميادين:

- الوحدة: متر.
- النظام: Right-Handed.
- المحاور المرجعية: `X = East`, `Y = North`, `Z = Up`.
- نقطة الأصل واتجاه الشمال والمرجع الجغرافي توثق في Project Configuration.

تشغيل Three.js الحالي يستخدم `Y-Up`. لا يغيّر هذا المعيار المحرك. يجب أن ينفذ
Model Adapter تحويلًا صريحًا، بإصدار واختبار، من الإطار المرجعي `Z-Up` إلى إطار
التشغيل `Y-Up`. يمنع إجراء تحويلات غير موثقة داخل مكونات العرض.

## 8. هوية العنصر من الرقمي إلى الفيزيائي

يجب أن يتطابق ID بنسبة 100% بين:

- سجل الكيانات.
- عقد الحالة التشغيلية.
- عقدة GLB/GLTF أو جدول الربط.
- ملف STL/3MF أو الجزء القابل للتصنيع.
- القطعة الفيزيائية.
- سطح الإسقاط أو الـMask المرتبط.
- السيناريو والقرار والمسار المرتبط.

كل قطعة قابلة للفك تحمل ID محفورًا أو DataMatrix غير ظاهر للمستخدم النهائي، ولا
يجوز إعادة استخدام ID بعد حذف عنصر.

## 9. معيار المجسم الفيزيائي

### 9.1 المتطلبات العامة

- تصميم Modular يسمح بفك المنطقة واستبدالها دون إعادة تصنيع كامل المجسم.
- واجهة تثبيت متكررة باستخدام Alignment Pins أو مغناطيس أو حل مكافئ مؤهل.
- قاعدة مستقرة قابلة للنقل والصيانة والوصول للكابلات والعلامات المرجعية.
- سطح مطفي ومحايد بلا لمعان أو ألوان تؤثر في الإسقاط.
- المادة تختار حسب الحرارة، والنقل، والسلامة، والعمر المتوقع.
- PLA Matte مسموح للمجسمات الداخلية بعد اجتياز عينة القبول، وليس المادة الوحيدة.

### 9.2 سماحات التصنيع

- دقة المقياس الكلية: `±0.5%`.
- تفاوت أبعاد القطعة: `±0.5 مم` أو `±0.5%`، أيهما أكبر.
- الفاصل الظاهر بين القطع بعد التجميع: لا يتجاوز `1 مم` في المناطق الحرجة.
- استواء قاعدة `PDT-M`: الانحراف لا يتجاوز `2 مم`.
- إعادة وضع القطعة بعد فكها: تفاوت لا يتجاوز `1 مم`.
- لا تقبل أسطح لامعة أو ملتوية أو شفافة دون اعتماد خاص.

### 9.3 ارتفاع المجسم والظلال

لا يثبت ارتفاع عام لكل الفعاليات. يحدد الحد الأقصى بواسطة Projection Study
تختبر الظلال، وعمق التركيز، وزاوية الرؤية، ومناطق الحجب. إذا فشل بروجكتر واحد
في تغطية الأسطح الحرجة، ينتقل المشروع إلى تصميم متعدد البروجكترات أو يعاد تصميم
الهندسة، ولا تخفى المشكلة بالبرمجيات.

## 10. معيار معدات الطباعة

المعدات المؤهلة يجب أن تحقق:

- تقنية FDM مغلقة للمشاريع الداخلية القياسية.
- حجم طباعة يلائم وحدات الملف المختار.
- معايرة آلية واستئناف بعد انقطاع الكهرباء.
- دعم فوهات 0.4 و0.6 مم على الأقل.
- ملفات طباعة محفوظة بإصدار، ومادة، وفوهة، وProfile موثق.
- عينة First Article ناجحة قبل بدء الدفعة.
- فحص أبعاد وربط ID لكل قطعة قبل التجميع.

الفوهة 0.6 مم هي المرجع للكتل الكبيرة، و0.4 مم للتفاصيل، ما لم يثبت اختبار
القبول خلاف ذلك.

## 11. معيار الإسقاط

### 11.1 المتطلبات العامة

- مصدر ضوء Solid-State أو Laser.
- دقة أصلية WUXGA على الأقل لملف `PDT-M`.
- تحكم شبكي LAN أو RS232.
- تركيب ثابت ومؤمّن بحامل مهني وسلك سلامة.
- Lens Shift بصري مفضل.
- النظام البرمجي يدعم منطقيًا مخرجين منذ البداية، ولو ركّب بروجكتر واحد.
- الدقة والسطوع والعدسة وThrow Ratio والعدد تحددها Projection Study.
- لا يعتمد أي جهاز من ورقة المواصفات فقط؛ يلزم اختبار على عينة فعلية.

### 11.2 Projection Study الإلزامية

توثق:

- أبعاد القاعدة والمساحة النشطة.
- أعلى نقطة وتوزيع الارتفاعات.
- موضع البروجكتر ونطاق الرمي والعدسة.
- السطوع المقاس عند سطح المجسم.
- إضاءة الغرفة في وضع العرض والخدمة.
- الظلال والأسطح الحرجة والمناطق المحجوبة.
- الدقة المطلوبة لأصغر مسار أو رمز أو نص.
- خيار الجهاز الواحد مقابل تعدد الأجهزة.
- مخطط الحامل والكابلات والتهوية والصيانة.

## 12. Projection Gateway وعقد الربط

### 12.1 فصل المسؤوليات

- Mayadeen OS يملك الحالة التشغيلية والقرار والسياق.
- Projection Gateway يترجم الحالة إلى أوامر عرض بإصدار محدد.
- Vendor Adapter يترجم العقد إلى Media Server أو Projection Renderer مؤهل.
- البروجكتر يعرض Video Output فقط ولا يتصل مباشرة بعقد الأعمال.

### 12.2 البروتوكولات

- REST للتهيئة، والـManifest، والـSnapshot، وإدارة ملفات المعايرة.
- WebSocket للتحديثات اللحظية والأوامر والإقرار بالاستلام.
- يجوز للـAdapter استخدام OSC داخليًا، لكن لا يصبح OSC عقد المنصة الأساسي.

كل رسالة لحظية تتضمن على الأقل:

```text
schemaVersion
eventId
venueId
modelId
entityId
stateContext
revision
timestamp
correlationId
sequence
command
payload
```

على المستقبل إرسال `ack` أو خطأ منظم. بعد انقطاع الاتصال يجب طلب Snapshot كامل
ثم متابعة Deltas من Revision معروف؛ لا يجوز افتراض أن آخر صورة ما زالت تمثل
الحالة الحية.

## 13. حالات الاتصال والفشل

- يعرض انقطاع الاتصال بوضوح على واجهة المشغل.
- لا تعرض الحالة المخزنة كأنها Live دون وسم واضح.
- يتوفر Blackout آمن من واجهة المشغل ومن إجراء محلي.
- يجب أن يعمل مخرج العرض الأساسي دون اعتماد إلزامي على الإنترنت.
- يحتفظ النظام بآخر Configuration وCalibration Profile معتمدين محليًا.
- بعد الاستعادة، يتحقق من الإصدارات قبل إعادة العرض التشغيلي.

## 14. Calibration Profile

كل ملف معايرة يرتبط إلزاميًا بـ:

- `calibrationProfileId`
- `calibrationVersion`
- `modelId` و`modelVersion`
- Hash ملف العرض.
- `physicalRevision`
- معرّف كل بروجكتر ورقمه التسلسلي.
- معرّف الحامل وموضعه وحالة ختمه أو علامته.
- الدقة والـViewport والـWarp والـMask والـBlend والـKeystone.
- علامات المعايرة المستخدمة.
- التاريخ والمنفذ والمراجع.
- نتيجة اختبار القبول.

إذا لم تتطابق هذه الإصدارات، يمنع وضع التشغيل التشغيلي ويطلب فحصًا أو إعادة
معايرة. يسمح فقط بوضع صيانة موسوم بوضوح.

## 15. معايير القبول

هذه القيم أهداف قبول إلزامية للإصدار 1.0، ويجب قياسها في أول Prototype مادي.
تسجيلها كمعيار لا يعني أنها تحققت في المنتج الحالي.

### 15.1 البيانات والهوية

- تطابق IDs بين السجل والنموذج وملفات الطباعة والمجسم: `100%`.
- صفر IDs مكررة أو مجهولة.
- نجاح Schema Validation والتحقق من الإصدارات والـHashes.
- فصل واضح بين Demo وBaseline وScenario.

### 15.2 المجسم

- اجتياز سماحات الأبعاد والاستواء والفواصل المحددة.
- فك وإعادة كل وحدة دون فقد المحاذاة.
- عدم وجود تشوه أو لمعان مؤثر على الأسطح المعتمدة للإسقاط.

### 15.3 الإسقاط

بعد تسخين وتشغيل النظام 30 دقيقة:

- تغطية `100%` للأسطح الحرجة و`98%` على الأقل للأسطح المحددة للعرض.
- الخطأ الوسيط في `PDT-M` لا يتجاوز `3 مم`.
- `P95` لخطأ التطابق لا يتجاوز `5 مم`.
- صفر مناطق حرجة مخفية بسبب الظل.
- حفظ واستعادة المعايرة بعد إعادة التشغيل.
- في النظام متعدد البروجكترات: خطأ التداخل لا يتجاوز بكسلين.
- اجتياز التباين والوضوح في ظروف الغرفة الحقيقية.

### 15.4 الأداء والاستمرارية

- زمن التحديث من المنصة إلى الصورة: `P95 ≤ 200 ms`.
- حد أدنى مستقر `30 fps`؛ والهدف `60 fps` للحركة التنفيذية.
- تشغيل متواصل 8 ساعات دون انهيار أو تسرب ذاكرة مؤثر.
- استعادة محطة العرض خلال دقيقتين من إعادة التشغيل.
- فحص واستعادة سريعة للمعايرة خلال 10 دقائق إذا لم تتحرك الأجهزة.

### 15.5 السلامة

- حامل وسلك سلامة معتمدان لكل بروجكتر مرتفع.
- تهوية ومسافات صيانة حسب تعليمات المصنع.
- إدارة كابلات وحماية كهربائية وحساب حمل موثق.
- UPS لمحطة التحكم والعرض بحجم مبني على الحمل المقاس وهامش مناسب.
- لا يعتمد UPS للطابعة قبل التحقق من أقصى قدرة وذروة التسخين.
- زر أو إجراء Blackout واضح ومختبر.

## 16. حزمة التسليم الإلزامية

لا يغلق المشروع دون:

- المصدر الهندسي المعتمد أو مرجعه المحكوم.
- GLB/GLTF التشغيلي.
- STL/3MF للتصنيع.
- Entity Register.
- Model Manifest والـHashes والإصدارات.
- Physical Part Register.
- Project Configuration.
- Projection Study.
- Calibration Profile.
- مخطط التركيب والكابلات والطاقة والشبكة.
- نتائج Factory Acceptance Test وSite Acceptance Test.
- نسخة احتياطية قابلة للاستعادة.
- دليل التشغيل وBlackout وإعادة المعايرة.
- قائمة قطع الغيار والمواد.
- سجل الاستثناءات والـWaivers إن وجدت.

## 17. الحماية من Vendor Lock-in

- تستخدم صيغ GLB/GLTF وSTL/3MF وJSON حيثما أمكن.
- عقود REST/WebSocket تحمل `schemaVersion` ولا تعتمد API مورّد داخل Domain Model.
- كل Media Server أو Projection Renderer خارجي يعمل خلف Vendor Adapter.
- ملفات المعايرة تصدر بصيغة موثقة يمكن تحويلها.
- البيانات والـIDs والقرارات تظل ملك Mayadeen OS.
- يجب وجود إجراء Export واختبار استعادة دون خدمة سحابية خارجية.
- لا يقبل جهاز يمنع التشغيل المحلي أو الوصول إلى البيانات اللازمة دون بديل معتمد.

## 18. إدارة التغيير

يستخدم المعيار Semantic Versioning:

- `Major`: تغيير يكسر العقد أو الإحداثيات أو هوية العناصر أو القبول.
- `Minor`: قدرة جديدة متوافقة مع المشاريع السابقة.
- `Patch`: تصحيح لا يغير السلوك المطلوب.

قواعد التغيير:

1. لا يعدل هذا الملف بصمت.
2. تغيير Core Standard يحتاج موافقة أحمد، ومراجعة CTO، ومراجعة قائد AV/Spatial.
3. تحديث Approved Equipment List لا يغير Core، لكنه يحتاج اختبار تأهيل.
4. كل مشروع يجمّد نسخة Core وProfile وAEL وProject Configuration عند البدء.
5. المشروع المكتمل لا يهاجر إلى إصدار جديد تلقائيًا.
6. الاستثناء يحتاج Waiver مكتوبًا يحدد السبب والمخاطر والمالك والتعويض وتاريخ الانتهاء.
7. أي استبدال من المورد يحتاج Regression Test واعتمادًا مكتوبًا.

## 19. إثبات المطابقة

لا يجوز وصف أي تركيب بأنه مطابق لمعيار ميادين إلا بوجود:

- Project Configuration مكتمل.
- معدات من AEL أو Waiver معتمد.
- Model Manifest متطابق.
- تقارير قبول ناجحة.
- Calibration Profile معتمد.
- توقيع مسؤول المنصة، وقائد AV/Spatial، وصاحب الاعتماد النهائي.

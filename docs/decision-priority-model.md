# نموذج أولوية القرار

**الإصدار:** `3C.1-1.0`
**النوع:** قواعد حتمية، وليس ذكاءً اصطناعياً.

## لماذا تغير النموذج

**Evidence:** النموذج السابق جمع أثر التشغيل وفجوات الدليل والثقة والاعتماد في درجة واحدة. كان القرار الضعيف البيانات يرتفع في الطابور وكأن أثره التشغيلي أعلى، بينما قد لا يصل قرار حرج موثق إلى تصنيف عاجل.

**Decision:** تعرض المنصة درجتين مستقلتين من 0 إلى 100. لا تدخل أي فجوة بيانات في درجة الأثر التشغيلي.

## 1. أولوية التشغيل

`operationalPriorityScore` يجيب: ما شدة الحاجة إلى القرار بسبب الأثر والوقت؟

| العامل | الحد الأعلى |
| --- | ---: |
| الاستعجال | 20 |
| الأثر التشغيلي العام | 15 |
| أثر السلامة | 20 |
| أثر الزائر | 10 |
| أثر الجدول | 10 |
| أثر الاعتماديات | 10 |
| ضغط الموعد | 15 |
| **المجموع النظري** | **100** |

التطبيع: `round(clamp(raw / 100 * 100, 0, 100))`. تحفظ القيمة الخام داخل `diagnostics` فقط ولا تعرض كقيمة تشغيلية أساسية.

التصنيف: `75–100 عاجلة`، `55–74 مرتفعة`، `30–54 متوسطة`، `0–29 منخفضة`. القرار المغلق يحصل على أولوية تشغيلية صفرية لأنه لا يمثل عملاً مفتوحاً.

## 2. عناية جودة البيانات

`dataQualityAttentionScore` يجيب: ما مقدار العمل المطلوب لاستكمال الثقة والدليل والسلطة؟

| العامل | الحد الأعلى |
| --- | ---: |
| فجوة الثقة | 25 |
| فجوة الدليل | 30 |
| فجوة الاعتماد | 20 |
| فجوة جودة المصدر | 15 |
| فجوة الملكية أو السلطة | 10 |
| **المجموع النظري** | **100** |

التصنيف: عناية عاجلة، مرتفعة، متوسطة، أو منخفضة. الدرجة العالية هنا لا تعني أن القرار حرج تشغيلياً.

## ترتيب الطابور

1. أولوية التشغيل تنازلياً.
2. الموعد الأقرب.
3. عناية جودة البيانات تنازلياً.
4. معرف القرار بترتيب رقمي ثابت.

تعرض الواجهة أقوى عوامل كل درجة وشرحاً عربياً مستقلاً. يمكن لقرار حرج موثق أن يصل إلى `عاجلة`، ويمكن لقرار منخفض الأثر ضعيف البيانات أن يحتاج عناية بيانات مرتفعة من دون تضخيم شدته التشغيلية.

## ضبط التجربة

يجمد الإصدار `3C.1-1.0` طوال أي pilot معتمد. تغيير وزن أو حد أو قاعدة ترتيب يحتاج إصداراً جديداً، حالات مرجعية، وموافقة أحمد. لا يجوز مقارنة نتيجتي إصدارين كأنهما مقياس واحد.

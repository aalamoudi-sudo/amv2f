# ADR-004: تجربة قيادة عامة وتنظيم المنتج

- **الحالة:** مقبول محليًا في Stage UX.1
- **السياق:** تراكم المساحات التقنية والتشغيلية في شريط واحد جعل قدرات صحيحة تقنيًا أصعب في الفهم والتشغيل، من دون أن يبرر تغيير عقود الحقيقة.

## القرار

تنظم الواجهة في خمس مناطق منتج عربية RTL: القيادة، العمليات، المكان، التجربة، والإدارة التقنية. تستخدم طبقة UI-only في `src/ux/commandExperience.ts` ولا تضيف domain contract أو schema أو API.

تعرّف الواجهة ثلاثة presentation presets: تنفيذي، تشغيلي، وتقني. هي إعدادات عرض صريحة وليست RBAC ولا مصادقة ولا تفويضًا إنتاجيًا. تبقى المساحات التقنية في درج واضح وتستمر lazy-loaded.

البحث العالمي يبني فهرسه من بيانات وقت التشغيل المنظمة والحزم المرشحة الصريحة، ويحصر النتائج في scope الفعالية الحالية. يبقى المعرف المكاني المشترك في store هو جسر التحديد بين قائمة و2D و3D والقرار والجاهزية وIoT.

## البدائل المرفوضة

1. الإبقاء على شريط مسطح لكل المختبرات: يخلط دور المشغّل مع الفني ويزيد الحمل المعرفي.
2. استبدال التنقل بنظام أدوار أو إخفاء صلاحيات: غير مصرح، ولا توجد identity/authorization إنتاجية.
3. نسخ بيانات بحث ثابتة في الواجهة: يخرق event isolation ويجعلها غير قابلة لإعادة الاستخدام.
4. نقل selection أو trust state إلى backend: تغيير عقد خارج نطاق UX.1.

## النتائج

- تظل Core event-agnostic وvendor-neutral، ويمكن لحزمة فعالية جديدة استخدام البنية من بياناتها المنظمة.
- الروابط العميقة القديمة محفوظة، وتضاف `executive` و`spatial` دون fork لمسارات العمل.
- تظل candidate/demo/baseline/scenario/reported/verified حالات مستقلة ومعلنة.
- يلزم اختبار مستخدمين حقيقيين قبل أي ادعاء بأن ترتيب المعلومات الأمثل لجميع الأدوار.

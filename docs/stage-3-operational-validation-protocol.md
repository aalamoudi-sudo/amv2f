# بروتوكول التحقق التشغيلي للمرحلة الثالثة

## الغرض وحدود الادعاء

يختبر البروتوكول فرضية غير متحققة: هل تساعد مَيادين المستخدم على فهم قرار تشغيلي أسرع وبدقة أعلى من طريقته الحالية؟ لا تثبت بيانات العرض أو عينة صغيرة قيمة تشغيلية، ولا يجوز تعميم نتيجة pilot على تشغيل حي.

## المهمة الموحدة

> حدد القرار الأعلى أولوية، واشرح سبب أهميته، وحدد المالك والإجراء المطلوب، وحدد نقص الدليل أو السلطة، واشرح أثر التأخير.

## الواجهات المقارنة

1. قائمة تشغيلية أو جدول تقليدي.
2. مخطط ثنائي الأبعاد.
3. مشهد ثلاثي الأبعاد.
4. عرض هجين: قائمة + مخطط ثنائي + مشهد ثلاثي.

لا توجد فرضية مسبقة أن 3D أفضل. إذا تفوقت القائمة أو 2D لمهمة ما، يوصى بذلك التمثيل لتلك المهمة.

## تصميم الحالات

- استخدم 5–10 قرارات حقيقية من نوع حدث واحد في الجولة الأولى، بعد إخفاء المعلومات الشخصية الحساسة.
- أنشئ عدة حالات متكافئة في التعقيد، مع إجابة مرجعية يعتمدها مالك القرار والسلطة المختصة.
- وازن ترتيب الواجهات بين المشاركين (Latin square أو ترتيب متوازن مماثل).
- لا تستخدم تسلسل الإجابات نفسه لكل مشارك، ولا تعِد الحالة نفسها بعد كشف الإجابة.
- لا تغيّر baseline أثناء التجربة؛ كل إدخال ونتيجة في مساحة التحقق المحلية فقط.
- جمد حزمة القرارات، الإجابات المرجعية، وإصدار الأولوية `3C.1-1.0` قبل أول مشارك. لا تغير الأوزان بين المشاركين.
- شغّل الحزمة أولاً عبر validator نفسه المستخدم في runtime. أي history gap أو malformed impact أو dangling evidence يوقف الحالة.

## القياسات

| المقياس | طريقة التسجيل |
| --- | --- |
| زمن القرار | من بدء المؤقت حتى إجابة نهائية، بالثواني. |
| اختيار الأولوية الصحيح | مطابق/غير مطابق للإجابة المرجعية. |
| تحديد المالك | صحيح/غير صحيح. |
| تحديد الإجراء | صحيح/جزئي/غير صحيح. |
| اكتشاف فجوة الدليل | صحيح/خطأ/فائت. |
| اكتشاف فجوة السلطة | صحيح/خطأ/فائت. |
| الأخطاء الحرجة | قرار قد يسبب فتحاً أو سلامة أو مساراً أو تنفيذاً خاطئاً. |
| جودة الشرح | تقييم ميسر من 1 إلى 5 وفق rubric ثابت. |
| ثقة المستخدم | 1 إلى 5 بعد كل حالة. |
| معايرة الثقة | مقارنة الثقة بصحة الإجابة؛ الثقة العالية في إجابة خاطئة سوء معايرة. |
| الحمل المعرفي | سؤال ذاتي 1–5 بعد كل واجهة، مع ملاحظة نقاط التردد. |
| الواجهة المستخدمة | `list`, `2d`, `3d`, `hybrid`. |

## العينة

- **Pilot استكشافي:** 5–8 مستخدمين؛ لا دلالة إحصائية مدعاة.
- **تحقق رسمي عند الإمكان:** 12–20 مستخدماً، حالات متكافئة متعددة، وتحليل paired لكل مستخدم.
- المستخدمون المستهدفون: قائد وردية، مشرف منطقة، HSE/أمن، لوجستيات، جودة، ومدير مشروع بحسب القرار.

## حدود النجاح الأولية

- أسرع بنسبة 25% على الأقل من الطريقة التقليدية الحالية.
- 90% على الأقل إكمال صحيح.
- صفر أخطاء حرجة.
- جودة شرح 4/5 على الأقل.
- تحديد صحيح لفجوتي الدليل والسلطة.

لا يكفي تحسن الزمن إذا انخفضت الدقة أو ظهرت ثقة زائدة. النجاح يُحسب لكل مهمة وتمثيل، لا كمعدل يخفي اختلاف الأدوار.

## قواعد الإيقاف وإعادة التصميم

- أوقف الحالة إذا كشف الاختبار بيانات شخصية أو دفع المستخدم إلى ادعاء اعتماد غير موجود.
- ارفض التمثيل لمهمة محددة إذا كان أبطأ بلا تحسن دقة قابل للقياس.
- أعد تصميم نموذج الأولوية إذا تكرر اختيار خاطئ سببه score أو إذا خلط المستخدم الأولوية بالثقة.
- أعد تصميم العلاقة إذا فهم المشاركون `affected` كسببية مثبتة دون دليل.
- لا تنتقل إلى Stage 4 بناء على هذه التجربة.
- ألغ الجولة إذا تغيرت الحزمة أو نموذج الأولوية بعد بدء المشاركين؛ ابدأ نسخة تجريبية جديدة بدلاً من خلط النتائج.

## مخرجات الجولة

ملف نتائج محلي CSV/JSON، سجل أخطاء حرجة منزوع الهوية، مقارنة paired، ملخص نوعي، قرار قبول/رفض لكل تمثيل ومهمة، وقائمة claims المسموح بها. إعادة ضبط مساحة التحقق تمسح المعاينة والسجلات المقبولة والنتائج والمؤقت. يحتاج استخدام قرارات حقيقية، الإجابات المرجعية، المشاركين، تعريف الخطأ الحرج، وأي نشر خارجي إلى موافقة أحمد. لا تبدأ المنصة pilot تلقائياً.

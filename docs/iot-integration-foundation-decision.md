# قرار تأسيس تكامل إنترنت الأشياء المحايد للمورّد

**المرحلة:** Stage 3F.0 — Vendor-Neutral IoT Observation Foundation  
**الحالة:** مصرح بالتنفيذ المحلي  
**تاريخ القرار:** 2026-07-16  
**صاحب القرار:** أحمد  
**نطاق التصريح:** عقود ومحاكيات واختبارات وواجهة محلية فقط

## الملخص التنفيذي

تحتاج المنصة إلى استقبال قراءات أجهزة مختلفة وربطها بالفعالية والموقع والعنصر
المكاني من دون جعل نوع الجهاز أو المورّد جزءًا من قلب المنصة. البنية الحالية في
Stage 3D تحتوي أصلًا على `sensor` و`CaptureEnvelope` وProvenance ومنع التكرار
والعمل دون اتصال وسجل أحداث غير قابل للمحو. لذلك لا يُنشأ مسار IoT موازٍ؛ بل
تضاف طبقة توصيف وتحقيق للقراءة قبل دخولها إلى مسار الحقيقة التشغيلية القائم.

هذه المرحلة لا تربط جهازًا حقيقيًا، ولا تنشئ Backend، ولا تختار Broker، ولا
تدّعي تغذية حية. هدفها إثبات أن المنصة تملك عقدًا محايدًا يمكن أن تمر عبره
قراءات موردين مختلفين مع بقاء هوية العناصر والثقة والسياق والإسقاط تحت سيطرة
Mayadeen.

## المشكلة التشغيلية

- **المستخدم الأساسي:** مشغل مركز القيادة ومسؤول التكامل.
- **القرار المدعوم:** هل القراءة صالحة ومتصلة بالعنصر الصحيح وحديثة بما يكفي
  لتُحفظ كملاحظة تشغيلية مبلّغة؟
- **الإجراء:** قبول القراءة محليًا، رفضها، حجرها لقدمها، حجب تكرارها، أو رفع
  تعارضها للمراجعة.
- **النتيجة المستهدفة:** مصدر واحد للحقيقة يمنع القياس المجهول أو القديم أو
  المتعارض من تغيير الجاهزية أو الـBaseline تلقائيًا.
- **تكلفة الفشل:** قرار خاطئ، ثقة زائفة في حالة الموقع، تكرار أثر تشغيلي، أو
  ربط قراءة بجهاز/منطقة غير صحيحة.

## ما هو دليل وما هو استنتاج

### دليل

- MQTT 5 بروتوكول Publish/Subscribe خفيف، يدعم درجات تسليم مختلفة وحالة جلسة
  وانتهاء صلاحية الرسالة، لكنه لا يضمن وحده Exactly-once على امتداد النظام.
- W3C WoT Thing Description 1.1 يقدّم وصفًا مشتركًا لبيانات الجهاز وخصائصه
  وأفعاله وأحداثه وروابط البروتوكول والأمن.
- CloudEvents 1.0.2 يقدّم غلافًا محايدًا للأحداث بين الأنظمة.
- NISTIR 8259A يضع قدرات أساسية للأجهزة مثل الهوية والتهيئة وحماية البيانات
  وتقييد الواجهات والتحديث الآمن والإبلاغ عن الحالة الأمنية.
- Stage 3D الحالي يملك بالفعل بوابة الالتقاط، Provenance، بصمة الحمولة،
  Idempotency، سجلًا Append-only، وعزل السياقات.

### استنتاج

يمكن استخدام MQTT 5 لاحقًا كوسيلة نقل، وWoT TD كوصف اختياري للجهاز،
وCloudEvents كغلاف تبادل، بينما يبقى `CaptureEnvelope` وسجل الأحداث في
Mayadeen هما العقد القانوني ومصدر الحقيقة.

### افتراض

أول جهاز حقيقي سيستطيع إرسال JSON عبر Gateway أو API، أو يمكن تركيب Adapter
عليه. هذا الافتراض لم يُختبر بعد.

## أبسط بديل موثوق

ملف CSV/JSON يدوي يحمّله المشغل ويحتوي على `deviceId` و`datastreamId` والقيمة
والوحدة والوقت والعنصر. هذا البديل أرخص وأسهل، وسيبقى معيار المقارنة في مختبر
الجهاز الحقيقي. إذا لم يخفض الربط الحي التأخير والأخطاء مقارنة به، فلا يوجد
مبرر لشراء بنية Broker أو أجهزة إضافية.

## القرار المعماري

```text
Device / Vendor Protocol
        ↓
Replaceable Edge Adapter
        ↓
Device & Datastream Registry
        ↓
Canonical IoT Observation
        ↓
Existing CaptureEnvelope + Provenance + Integrity Gateway
        ↓
Append-only Operational Event Repository
        ↓
Reported observation (not verified state)
        ↓
2D / 3D / Geospatial / Physical outputs after governed verification only
```

### عقود Mayadeen الثابتة

- هوية مستقرة للجهاز منفصلة عن هوية الأصل أو المنطقة.
- تعريف Datastream للقيمة والنوع والوحدة والحدود الفيزيائية وحد التشغيل.
- ربط صريح بـEvent/Venue/Entity و`mappingVersion`.
- `observedAt` و`receivedAt` منفصلان مع جودة الوقت.
- Sequence وBoot/Session epoch لكشف الفجوات وعدم الاعتماد على الوقت وحده.
- بصمة قانونية ومفتاح منع تكرار؛ المحتوى المختلف تحت المفتاح نفسه تعارض.
- القراءة تبقى `reported` ولا تغيّر الجاهزية أو القرار أو Baseline تلقائيًا.
- Stale/Offline/Unknown/Disabled حالات ظاهرة ولا يجري إخفاؤها بآخر قيمة.

### ما يبقى قابلًا للاستبدال

- Broker وEdge Runtime وCloud/On-prem وقاعدة البيانات وPKI/HSM.
- بروتوكول الجهاز الأصلي؛ لا يُفرض MQTT على كل جهاز.
- MQTT وHTTP وModbus وBLE وUWB وONVIF وغيرها تدخل خلف Adapters.
- الفيديو لا يمر عبر MQTT؛ تمر Metadata والتنبيهات فقط في عقد الأحداث.

## Build / Buy / Partner / Delay

| القرار | النطاق |
| --- | --- |
| Build | العقود، سجل الأجهزة، ربط Thing/Asset، التحقق، Adapter SDK، Provenance، Idempotency، Conformance والواجهة |
| Buy | Broker إنتاجي، PKI/HSM، إدارة أسرار، Observability بعد نجاح المختبر |
| Partner | الأجهزة، المعايرة، البوابات، الشبكات، التركيب والشهادات الميدانية |
| Delay | شراء الأجهزة، Live MQTT/HTTP، التحكم بالأجهزة، Cloud SDK، Camera video، AI والـSimulation |

## ضوابط الأمن وعدم الارتهان

- ممنوع وضع Credentials أو Tokens أو عناوين إنتاجية داخل Event Package أو
  المتصفح أو Git.
- المتصفح لا يتصل مباشرة بـBroker إنتاجي.
- لكل جهاز إنتاجي لاحقًا هوية مستقلة قابلة للتدوير والإبطال، ويفضل mTLS.
- Broker ليس مصدر الحقيقة ولا يملك Event Ontology.
- لا Last-write-wins ولا Exactly-once claim؛ التصميم يتحمل At-least-once مع
  Idempotency وAppend-only replay.
- Retained messages، إن استُخدمت، للحالة المرغوبة أو Availability فقط وليست
  سجل Telemetry تاريخيًا.
- الأوامر والتحكم خارج هذه المرحلة، وأي أمر مستقبلي يحتاج Expiry وAuthority
  وAcknowledgement مستقلين.

## الاعتماديات والمخاطر

| الاعتمادية أو الخطر | الضابط الحالي |
| --- | --- |
| ساعة الجهاز غير موثوقة | حفظ وقت الجهاز ووقت الاستلام وجودة الوقت منفصلة |
| قراءة قديمة أو خارج الترتيب | حجر Stale وعدم استبدال أحدث قراءة مقبولة |
| تكرار أو إعادة إرسال | بصمة قانونية + Idempotency + Sequence |
| جهاز أو Stream مجهول | رفض قبل إنشاء حدث تشغيلي |
| انقطاع الشبكة | Queue محلية ومحاكاة Store-and-forward مع Replay حتمي |
| Vendor lock-in | عقود Mayadeen + Adapters قابلة للاستبدال + لا Vendor SDK في Core |
| تضخم البيانات | حدود حمولة وBackpressure وRetention في مرحلة Backend |
| سرية وخصوصية | لا بيانات شخصية أو عناوين إنتاجية في المختبر |

## معايير نجاح المرحلة المحلية

1. تحقق 100% من الجهاز والـDatastream والعنصر قبل القبول.
2. القراءة الصالحة تنشئ `sensor.observed` بحالة `reported` فقط.
3. صفر تغييرات في Baseline/Readiness/Decision/verified projection من قراءة
   محاكية غير متحققة.
4. التكرار المطابق لا ينشئ أثرًا ثانيًا، والمفتاح نفسه مع محتوى مختلف يُحجر
   كتعارض.
5. القراءة القديمة أو خارج الترتيب لا تستبدل أحدث قراءة صالحة.
6. Replay دون اتصال حتمي، والإعادة الثانية Duplicate.
7. تهيئتان مختلفتان تعملان من دون منطق خاص بنوع فعالية أو مورد.
8. جميع حالات الرفض تعرض سببًا عربيًا آمنًا مع Path، من دون أسرار.
9. لا طلبات شبكة خارجية ولا Dependency أو Vendor SDK جديد.
10. واجهة RTL تحمل دائمًا: «بيانات أجهزة محاكاة محلية — لا أجهزة ولا تغذية
    تشغيلية حية».

## بوابة الانتقال إلى جهاز حقيقي

لا يبدأ الربط الحقيقي قبل اعتماد أحمد لحالة استخدام واحدة، جهاز واحد، مالك
المصدر، معرّفات Event/Venue/Entity، سياسة الوقت والهوية، حدود القياس، سياسة
الاحتفاظ، خطة الشبكة والأمن والرجوع، ومقاييس قبول. عندها فقط نختبر Brokerين أو
Adapterين بالعقود نفسها ونقارن المسار الحي بالاستيراد اليدوي.
